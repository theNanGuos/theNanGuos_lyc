# theNanGuos 文档架构重构设计

## 1. 设计状态

- 设计日期：2026-07-14
- 适用项目：theNanGuos（南郭先生们）
- 首要读者：项目维护者、后续开发者和 Coding Agent
- 设计结论：采用“主文档 + 技术专题 + Work Unit”的分层文档体系
- 实施边界：本文只定义目标结构；实际迁移由 `WU-DOC-001` 计划执行

## 2. 问题与目标

当前文档不是信息不足，而是多份文档同时承担产品需求、技术合同、实现设计和进度记录，导致以下问题：

1. `PRD.md` 同时包含产品需求、Agent/Tool 机制、记忆实现和完整 JSON 数据结构，产品视角被技术细节淹没。
2. `SPEC.md` 名义上是权威实现合同，但主要覆盖 Suno、部分记忆和知识库，缺少完整功能行为规格。
3. `INFORMATION_ARCHITECTURE.md` 已划分信息域，但以对象和字段罗列为主，缺少域关系、生命周期和跨域数据流。
4. `ARCHITECTURE.md` 的工程树使用英文注释，单靠空格缩进表达层级，且缺少技术选型与取舍依据。
5. `PLAN.md` 在基线计划完成后直接追加知识库“第 19 点”，把最终实施路线、增量任务和历史记录混在同一编号体系。
6. 字段、状态和规则在 PRD、SPEC、IA、架构之间重复，修改时容易只更新一份。
7. 当前除 `README.md` 外的根目录 Markdown 被 Git 忽略，新克隆仓库的 Coding Agent 无法读取正式设计事实。

本次重构目标：

- 人可以从入口文档快速建立全局认识，并明确下一步去哪里找细节。
- Coding Agent 可以根据问题类型定位唯一事实源，不需要在多份冲突文档间猜测。
- 产品行为、系统设计、数据合同、API 合同、实施任务和开发状态互不混用。
- 现有有效信息全部迁入新的权威位置，只删除重复副本和过时表述。
- 新功能不再通过任意追加章节进入主计划，而是通过领域编号 Work Unit 管理。

## 3. 总体分层

文档分为四层：

| 层级 | 回答的问题 | 文档 |
|---|---|---|
| 入口层 | 项目是什么、如何运行、应先读什么 | `README.md`、`docs/README.md` |
| 产品与行为层 | 为什么做、用户看到什么、系统应表现成什么 | `PRD.md`、`SPEC.md`、`WEB_UI_DESIGN.md` |
| 技术设计层 | 系统如何组织、对象和协议如何定义 | `ARCHITECTURE.md`、`INFORMATION_ARCHITECTURE.md`、`AGENT_SYSTEM.md`、`DATA_MODEL.md`、`API_SPEC.md` |
| 执行与证据层 | 按什么顺序实施、任务边界是什么、现在做到哪里 | `PLAN.md`、`work-units/*.md`、`STATUS.md` |

核心规则：

1. 同一事实只在一个权威文档中完整定义。
2. 其他文档只保留读者所需的摘要，并使用相对链接指向权威定义。
3. 文档中的实现路径必须与仓库代码对应；不能用设计愿景冒充已实现状态。
4. 完成状态和验证证据只写入 `STATUS.md`。
5. Mermaid 图必须附带文字关系表或步骤说明，不能让图成为唯一事实载体。

## 5. 文档职责

### 5.1 README.md

只承担项目入口：

- 产品一句话介绍和当前能力；
- 本地安装、启动和最小验证命令；
- 文档索引入口；
- 真实供应商凭据要求和当前限制。

不复制完整架构、API 字段或计划内容。

### 5.2 docs/README.md

作为正式文档地图，提供：

- 按读者目标组织的阅读路径；
- 每份文档的唯一职责；
- “问题 → 权威文档”索引；
- 文档维护规则和稳定标识约定。

### 5.3 PRD.md

PRD 回答“为什么做、为谁做、做什么”，建议结构：

1. 产品定位与目标；
2. 用户和使用场景；
3. 范围与非目标；
4. 核心用户流程；
5. 产品能力；
6. 核心对象词汇表；
7. 业务规则；
8. 产品级异常与边界；
9. 产品验收标准；
10. 相关技术文档链接。

Agent、Tool、记忆和知识库只保留产品能力摘要，例如“系统使用四个固定职责 Agent”以及“用户偏好与创作知识是两类不同的长期信息”。完整机制迁入 `AGENT_SYSTEM.md`。

PRD 可以列出 `Generation`、`SongSpec`、`TaskPlan`、`ScorePlan`、`Work`、`UserPreference` 等核心对象及产品含义，但不保留完整 JSON、字段约束和 Pydantic 规则。

### 5.4 SPEC.md

SPEC 是功能行为的权威规格，回答“系统对用户和调用方应如何表现”，不描述内部类、函数或目录实现。

建议按能力域编排：

1. 创作预览与方案确认；
2. 创建生成任务；
3. Agent 生成阶段和用户可见进度；
4. Suno 提交与轮询行为；
5. 停止等待和继续查询；
6. 成功结果、播放、封面和下载；
7. 作品列表与服务重启；
8. 默认偏好与风格偏好；
9. 创作知识库行为；
10. CLI 离线与提交模式；
11. 错误、安全和验收场景。

每个功能使用稳定 ID，例如 `FR-GEN-001`，并包含：

- 前置条件；
- 输入摘要；
- 主流程；
- 状态变化；
- 异常与恢复；
- 输出摘要；
- 验收场景；
- 对应 `DATA_MODEL.md` 和 `API_SPEC.md` 链接。

### 5.5 WEB_UI_DESIGN.md

保留五页导航、内容层级、组件、交互、响应式和视觉基线。页面字段只描述展示含义，字段类型和接口载荷链接到 `DATA_MODEL.md`、`API_SPEC.md`。

### 5.6 ARCHITECTURE.md

系统架构回答“组件为什么这样组织”，建议结构：

1. 架构目标与约束；
2. 系统上下文；
3. 总体架构与分层；
4. 技术选型与取舍；
5. 工程结构与模块职责；
6. 运行时组件；
7. 部署与进程模型；
8. 关键运行路径；
9. 安全、可靠性和错误边界；
10. 测试架构；
11. 扩展边界。

工程目录树必须：

- 使用 `├─`、`│`、`└─` 表示结构；
- 所有职责注释改为中文；
- 目录树之后增加“模块—职责—依赖—对应代码”的表格。

技术选型表至少解释 Vue 3、FastAPI、LangGraph、Pydantic、httpx、Markdown/YAML、单进程与本地文件存储的选择原因，并说明 MVP 暂不采用数据库、消息队列、向量数据库和跨进程恢复的理由。

### 5.7 INFORMATION_ARCHITECTURE.md

IA 回答“信息如何分域、如何流动、由谁拥有”，不再重复字段表。

保留并明确以下信息域：

- 用户输入域；
- 创作规划域；
- 运行状态域；
- 长期偏好域；
- 创作知识域；
- 外部协议域；
- 本地作品域；
- 页面展示域。

每个域记录：目的、拥有对象、写入方、读取方、生命周期、持久化位置和跨域关系。字段定义统一链接 `DATA_MODEL.md`。

### 5.8 AGENT_SYSTEM.md

Agent 专题统一承接原 PRD、SPEC 和架构中的以下内容：

- 四个 Agent 的职责、输入、输出和禁止行为；
- 确定性 Tool 的职责与边界；
- 固定 LangGraph 拓扑与节点职责；
- `TaskPlan` 的解释性作用和固定图的执行权威；
- DeepSeek 结构化输出与 Thinking Mode 边界；
- 单次运行 `GraphState`；
- 用户确认型长期偏好；
- 人工创作知识库及两阶段检索；
- Agent 职责视图；
- prompt 数据最小化、推理内容隔离、降级与可观测性；
- Agent 级测试策略。

### 5.9 DATA_MODEL.md

数据模型是领域对象和字段的权威来源，包含：

- 核心对象 UML；
- 对象目录和稳定 ID，例如 `DM-SongSpec`；
- Pydantic 字段、类型、必填性、默认值、枚举和约束；
- JSON 名称与 Python 名称映射；
- 对象间包含、引用和转换关系；
- 本地文件映射；
- 兼容性与版本策略；
- 必要的最小 JSON 示例。

产品含义由 PRD 定义，HTTP 传输载荷由 API_SPEC 定义；DATA_MODEL 不重复用户流程。

### 5.10 API_SPEC.md

API 合同分为三组：

1. 本地 FastAPI：预览、生成、列表、详情、停止、继续、媒体、偏好；
2. DeepSeek：结构化请求、JSON Output、Thinking Mode、重试和错误；
3. Suno：提交、详情查询、轮询状态、媒体字段和失败终态。

每个接口记录稳定 ID、方法、路径、认证、请求、响应、状态码、错误码、幂等性、超时、重试和安全边界。字段定义引用 `DATA_MODEL.md`，功能意图引用 `SPEC.md`。

### 5.11 PLAN.md

PLAN 只描述最终系统的规范化主路线，不充当历史记录或实时看板。

推荐阶段：

| 阶段 | 主题 |
|---|---|
| P1 | 工程基础与配置 |
| P2 | 数据模型与协议合同 |
| P3 | 用户偏好与创作知识 |
| P4 | LLM 与 Agent |
| P5 | LangGraph 编排与产物 |
| P6 | Suno、轮询与本地媒体 |
| P7 | FastAPI 与后台任务 |
| P8 | Web UI 与播放器 |
| P9 | 联调、视觉、安全和完整验收 |

PLAN 包含阶段依赖、目标产物、验收门槛、Milestone 映射和 WU 索引，但不保存完成勾选、当前状态或测试次数。

### 5.12 STATUS.md

STATUS 是唯一进度看板，包含：

- 当前项目结论；
- Milestone 状态；
- 当前 WU；
- WU 状态表；
- 最新验证证据；
- 阻塞、风险和下一步。

允许状态统一为：`planned`、`ready`、`in_progress`、`blocked`、`done`。状态名称需要在文档中同时给出中文解释。

## 6. 正式图表

文档只维护六类正式图：

| 图 | 权威文档 | 回答的问题 |
|---|---|---|
| 系统上下文图 | ARCHITECTURE | 用户、应用、DeepSeek、Suno、文件系统如何交互 |
| 组件关系图 | ARCHITECTURE | 前端、API、任务、图、适配器和存储如何依赖 |
| 信息域关系图 | INFORMATION_ARCHITECTURE | 输入、规划、状态、偏好、知识、协议和作品如何流动 |
| 生成时序图 | AGENT_SYSTEM | 预览、确认、两阶段检索、四 Agent 和 Suno 如何按时序协作 |
| 核心对象 UML | DATA_MODEL | Generation、SongSpec、ScorePlan、SunoTask、Work 如何关联 |
| 任务状态机 | SPEC | queued、running、stopped、interrupted、completed、failed 如何转换 |

图使用 Mermaid 保存可维护源代码。每张图之后必须有节点职责表、关系表或顺序说明，保证不支持 Mermaid 的阅读环境仍能获得完整信息。

## 7. Work Unit 设计

### 7.1 定位

Work Unit 是可独立实施、审查和验证的最小计划单元。它不等于 Phase 或 Milestone：

- Phase 表示系统建设的依赖顺序；
- Milestone 表示用户或项目可验证的阶段性结果；
- WU 表示具体可执行任务合同。

### 7.2 编号

统一格式：`WU-<AREA>-<NNN>`。

领域码：

| 领域码 | 范围 |
|---|---|
| CORE | 工程基础、配置和公共运行时 |
| DATA | 数据模型、Schema 和协议映射 |
| AGENT | LLM、Agent、prompt 和结构化输出 |
| KNOW | 用户偏好、记忆和创作知识 |
| GRAPH | LangGraph、GraphState 和节点编排 |
| SUNO | Suno、轮询和媒体保存 |
| API | HTTP API、后台任务和生命周期 |
| WEB | Web UI、状态管理和播放器 |
| QA | 联调、视觉、安全和验收 |
| DOC | 文档架构和治理 |

跨领域 WU 使用主要产物所属领域，其他领域以依赖 WU 表达，不创建组合领域码。

### 7.3 WU 内容

每个 WU 必须包含：

1. WU ID 和标题；
2. 所属 Phase 和目标 Milestone；
3. 背景与目标结果；
4. 依赖 WU；
5. 允许修改范围；
6. 明确非范围；
7. 设计事实源链接；
8. 预期产物；
9. 实施步骤；
10. 测试与验证；
11. 完成标准；
12. 风险与回滚边界；
13. 交接要求。

WU 文件不记录可变状态，不使用完成勾选。文件中统一写“实际状态见 `STATUS.md`”。

### 7.4 新增需求流程

新增范围固定执行：

1. 先更新 PRD、SPEC、架构或技术专题，确认目标状态；
2. 创建或调整 WU，明确范围、依赖、产物和验收；
3. 在 STATUS 将 WU 标为 ready 或 in_progress；
4. 实施并记录新鲜验证证据；
5. 将稳定能力整合进 PLAN 的逻辑阶段；
6. STATUS 标记 done；经验教训写入本地 `PROGRESS.md`。

知识库不再作为 PLAN 的“第 19 点”。目标能力分别归入 P3、P4 和 P5，已完成实施过程按实际证据整理为 `WU-KNOW-*`。

## 8. 稳定标识与引用

推荐标识：

- 功能：`FR-<AREA>-<NNN>`；
- 数据模型：`DM-<ObjectName>`；
- API：`API-<AREA>-<NNN>`；
- Work Unit：`WU-<AREA>-<NNN>`；
- Milestone：`M1` 至 `M5`；
- Phase：`P1` 至 `P9`。

标识一旦进入正式文档不得因章节重排而改变。标题可以优化，引用使用稳定 ID 和相对链接。

## 9. 迁移映射

| 当前内容 | 目标位置 | 迁移规则 |
|---|---|---|
| PRD 产品目标、流程、页面需求 | PRD、WEB_UI_DESIGN | PRD 保留能力；详细交互进入 UI 文档 |

| IA 信息域 | INFORMATION_ARCHITECTURE | 保留并补关系、生命周期和信息流 |
| IA 字段表 | DATA_MODEL | IA 只保留对象摘要和链接 |
| ARCHITECTURE 工程树 | ARCHITECTURE | 改为中文、显式树线和职责表 |
| ARCHITECTURE 技术机制 | ARCHITECTURE、AGENT_SYSTEM | 系统级留架构；Agent 细节下沉 |

## 10. Git 与忽略规则

实施完成后的目标：

- 根目录 Git 跟踪的 Markdown 仍只有 `README.md`；
- `docs/**/*.md` 是正式文档并纳入 Git；
- `docs/planning/work-units/*.md` 纳入 Git；
- 临时草稿使用明确的本地目录并被忽略；
- 根目录 `PROGRESS.md` 继续忽略；
- 运行产物、缓存、知识索引和本地凭据继续忽略。

迁移前必须检查现有 `.gitignore` 的 `/*.md` 规则只作用于根目录，避免误忽略 `docs/`。

## 11. 一致性与验收

`WU-DOC-001` 至少验证：

1. 现有 PRD、SPEC、IA、架构和 PLAN 的有效章节均有迁移去向；
2. 不丢失已确认的 Suno 字段、状态、轮询规则、记忆边界、知识库合同和 Web UI 行为；
3. PRD 不再包含完整字段级 JSON；
4. 字段级约束只能在 DATA_MODEL 或 API_SPEC 完整定义；
5. SPEC 覆盖全部用户可观察功能和异常行为；
6. 六张正式图均存在，且每张图有文字替代说明；
7. ARCHITECTURE 工程树使用中文注释和显式结构线；
8. PLAN 不包含实时状态或任意追加的“第 19 点”；
9. STATUS 使用 WU ID 且仍是唯一进度看板；
10. 所有正式文档可以从 `docs/README.md` 到达；
11. 所有相对链接有效；
12. Git 能跟踪正式 docs，同时继续忽略本地草稿和凭据；
13. 代码、测试、文档中的关键名称和状态枚举一致；
14. 运行文档检查后不存在空章节或未解释的占位符。

## 12. 风险与控制

### 信息迁移丢失

控制方式：先建立“原章节 → 目标章节”清单，再迁移内容；迁移完成前不删除旧文件。删除只发生在差异审查和链接检查之后。

### 文档再次重复

控制方式：在 `docs/README.md` 维护权威归属表；评审时检查完整 JSON、字段表、状态表和 Agent 机制是否出现多个定义副本。

### 图与文字漂移

控制方式：图只表达关系，文字表保存精确规则；同一 WU 内同时更新图和关系表。

### WU 过大或变成状态看板

控制方式：一个 WU 只产生一个可独立验收的结果；跨多个独立结果时拆分。WU 不记录状态，所有进度只进入 STATUS。

### 正式文档与实际代码不一致

控制方式：迁移以当前实现和测试为证据；未联调的真实供应商能力必须标记为设计合同或待验证，不能写成已完成事实。

## 13. 实施入口

后续实施必须先创建 `WU-DOC-001` 的详细计划。建议顺序：

1. 建立完整内容清单和迁移矩阵；
2. 创建目标目录、文档索引和文档骨架；
3. 迁移并去重产品与功能规格；
4. 迁移并补足技术专题；
5. 增加六张正式图和文字说明；
6. 重排 PLAN，建立 WU 规则和 WU 索引；
7. 将 STATUS 改为 WU 看板；
8. 调整 Git 跟踪与忽略边界；
9. 执行链接、术语、字段、状态和实现一致性审查。

在本文经用户复核通过前，不执行上述迁移。
