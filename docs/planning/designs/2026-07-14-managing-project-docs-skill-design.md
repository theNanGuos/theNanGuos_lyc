# managing-project-docs Skill 设计

## 1. 设计目标

创建个人 Skill `managing-project-docs`，用于：

- 为新建软件项目建立适合其规模的文档体系；
- 在已有项目中审计、重组和迁移重复、混乱或过时的文档；
- 为新增大型目标建立设计、计划和 Work Unit（WU）；
- 处理 PRD、SPEC、架构、代码和测试之间的事实冲突；
- 让项目维护者与 Coding Agent 能从同一组清晰、可验证的事实源工作。

Skill 安装位置：

```text
C:\Users\lyclyc_NSP\.codex\skills\managing-project-docs\
```

## 2. 核心原则

1. 先审计项目事实，再提出组织方案；用户确认后才创建、迁移或修改文档。
2. 不为目录完整而创建空洞文档；文档集合按项目规模和风险裁剪。
3. 当前代码与测试表示已实现行为，需求与设计可能表示目标行为；冲突必须显式标注，不得静默覆盖。
4. 一个事实只有一个详细权威来源，其他文档只保留摘要和链接。
5. `STATUS.md` 是唯一动态进度事实源；PLAN、WU 和专题文档不重复保存实时状态。
6. 小任务直接在对话中完成；大型目标进入 PLAN，并拆成多个上下文可控的 WU。
7. 已有项目重组遵循保留原文、可回溯、分批迁移和验证后清理。
8. 不覆盖用户未提交工作，不未经授权 commit、push、删除或部署。

## 4. 触发场景与三种模式

### 4.1 触发场景

- 新项目需要建立需求、规格、架构、计划和看板；
- 已有项目文档重复、过时、相互冲突或缺少清晰入口；
- 新增大型功能、架构调整或跨模块任务，需要 WU 拆分；
- 用户要求整理项目文档、制定开发计划、划分任务或更新进度看板；
- PRD、SPEC、架构、代码和测试之间存在事实冲突。

### 4.2 新建项目模式

1. 识别产品目标、技术栈、交付方式、规模和风险。
2. 给出核心文档套餐和条件型文档建议。
3. 用户确认后创建文档骨架。
4. 按目标与范围、PRD、核心对象、SPEC、ARCHITECTURE、条件型专题、PLAN/WU、STATUS 的顺序填充。
5. 不虚构完成度、测试结果或不存在的架构事实。

### 4.3 已有项目重组模式

1. 检查项目指令、Git 状态、README、代码入口、测试和现有文档。
2. 建立文档清单，区分当前实现、目标合同、历史记录、临时文件和未决冲突。
3. 建立“来源章节 → 目标事实源 → 处理动作 → 验证方式”的迁移矩阵。
4. 用户确认后分批创建新事实源并迁移内容。
5. 在内容、链接和入口验证通过前保留旧文档。
6. 最后归档或在获得授权后删除旧副本，并更新 STATUS。

### 4.4 新增任务模式

- 明显、局部、低风险、无设计决策且不改变公共行为的小任务，直接修改并运行必要的最小检查。
- 大型目标先登记在 PLAN；涉及方案权衡时增加设计文档；随后按领域和上下文边界拆成多个 WU。
- 小任务一旦暴露设计冲突、范围扩张、公共合同变化或跨模块风险，就升级为设计与 WU 流程。

统一工作流：

```text
识别场景
→ 审计项目事实
→ 判断规模与风险
→ 提出组织方案
→ 等待用户确认
→ 创建、迁移或修改
→ 检查链接与事实源
→ 更新 STATUS
```

## 5. 核心文档职责

所有项目默认具备以下文档，内容深度按规模裁剪：

| 文档 | 必须包含 | 不应包含 |
|---|---|---|
| `README.md` | 项目定位、启动入口、最短使用路径、正式文档入口 | 完整需求、详细架构、实时进度 |
| `docs/README.md` | 文档地图、按目标阅读路径、事实源归属、更新规则 | 各文档正文副本 |
| `PRD.md` | 产品定位、目标与非目标、用户与场景、核心流程、能力、核心对象词汇、业务规则、成功指标 | 完整 JSON、字段级 Schema、接口参数、实现步骤 |
| `SPEC.md` | 用户可观察功能、前置条件、主流程、状态、异常恢复、输出、验收场景、稳定功能 ID | 当前完成度、内部实现细节、大段字段定义 |
| `ARCHITECTURE.md` | 系统上下文、组件职责、数据流、部署形态、技术选型、质量属性、安全边界 | 产品需求全文、接口字段全集、实时进度 |
| `PLAN.md` | Phase、Milestone、大型目标、WU 索引、依赖、完成定义、风险、非目标 | 当前执行状态、完成勾选、动态测试数量 |
| `STATUS.md` | 当前结论、当前 WU、WU 看板、里程碑状态、阻塞、验证证据、下一步 | 详细设计、需求正文、长期计划说明 |

建议基础目录：

```text
docs/
├─ README.md
├─ product/
│  ├─ PRD.md
│  └─ SPEC.md
├─ architecture/
│  └─ ARCHITECTURE.md
└─ planning/
   ├─ PLAN.md
   ├─ STATUS.md
   ├─ designs/
   └─ work-units/
```

项目已有稳定命名和目录时，保持现有约定，只落实职责边界，不强制改名。

## 6. 条件型文档

| 文档 | 新增条件 | 核心内容 |
|---|---|---|
| `INFORMATION_ARCHITECTURE.md` | 多角色、多入口、多页面层级、复杂可见性 | 信息域、导航、页面层级、读写方、生命周期、可见性 |
| `DOMAIN_MODEL.md` | 术语易混淆、实体关系复杂、存在领域不变量 | 统一语言、实体、值对象、聚合、状态、不变量、领域 UML |
| `DATA_MODEL.md` | 共享 Schema、复杂持久化、迁移或兼容要求 | 字段、类型、约束、枚举、关系、存储和兼容规则 |
| `API_SPEC.md` | 公共 API、Webhook、供应商或跨团队协议 | 端点、输入输出、错误、重试、幂等、安全和版本 |
| `AGENT_SYSTEM.md` | LLM、RAG、MCP、Tool、多 Agent、记忆 | Agent、Prompt、Tool、状态、记忆、检索、安全和评估 |
| `WEB_UI_DESIGN.md` | 重要交互、视觉基线、多页面状态 | 页面结构、组件、状态、交互、响应式和视觉验收 |
| `SECURITY.md` | 权限、敏感数据、上传、支付、命令执行、公网部署 | 威胁边界、认证授权、数据保护、审计、密钥和安全验收 |
| `DEPLOYMENT.md` | 多环境、发布、迁移、回滚 | 环境、配置、部署、迁移、回滚和健康检查 |
| `TEST_STRATEGY.md` | 多测试层级、高风险链路、复杂验收 | 测试层级、责任、环境、覆盖矩阵、质量门和证据 |
| `ADR-*.md` | 重要长期决策且有多个合理方案 | 背景、决策、备选、理由、后果和替代条件 |
| `designs/*.md` | 大型目标在拆 WU 前需要方案评审 | 范围、方案、选定设计、边界、风险和验收 |
| `RUNBOOK.md` | 持续运行、值守和故障恢复 | 告警、诊断、恢复、升级和复盘入口 |

小项目可先把 API、数据和部署摘要放入 ARCHITECTURE；当某一专题形成独立事实源和独立读者目标时再拆分。

## 7. 项目规模与裁剪

项目规模综合判断用户角色、核心对象、模块与部署单元、外部系统、安全风险、团队协作、发布运维和需求变化速度。

### 7.1 小型项目

默认只使用七份核心文档。API、数据、部署作为架构章节。无条件不创建 IA、领域模型、安全专题或独立测试策略。

### 7.2 中型项目

通常增加 DATA_MODEL、API_SPEC、设计目录和 WU 目录，并按产品形态选择 IA、领域模型、UI、测试或安全文档。

### 7.3 大型项目

通常拆分 IA、领域模型、数据、API、安全、ADR、部署、运行手册和测试策略，但仍逐项通过条件矩阵决定，不把“全部文档”作为大型项目的定义。

### 7.4 条件增量

- 三个以上主要角色或复杂导航：考虑 IA。
- 复杂实体关系、术语歧义或领域不变量：增加 DOMAIN_MODEL。
- 多个共享 Schema、迁移或兼容要求：增加 DATA_MODEL。
- 公共接口、Webhook 或供应商协议：增加 API_SPEC。
- LLM、RAG、Agent、Tool 或长期记忆：增加 AGENT_SYSTEM。
- 权限、敏感数据、上传、支付或命令执行：增加 SECURITY。
- 多环境、迁移、回滚和值守：增加 DEPLOYMENT/RUNBOOK。
- 多测试层级或关键业务闭环：增加 TEST_STRATEGY。
- 重要长期方案选择：增加 ADR。
- 高保真原型或严格交互基线：增加 WEB_UI_DESIGN。

## 8. Work Unit 模型

大型目标不是一个 WU，而是 PLAN 中的 Phase、Milestone 或 Initiative，由多个 WU 组成。只有需要方案评审时才增加设计文档，不默认增加独立 Initiative 文件。

### 8.1 WU 定义

WU 是人和 Coding Agent 可以一次理解、实施、验证和交接的完整上下文单元。合格 WU：

- 只有一个主要结果和清晰完成定义；
- 背景能由 WU 和少量权威链接说明；
- 范围、非范围、输入、输出和依赖清晰；
- 有独立验证方法和可审查增量；
- 另一执行者无需重新推导整个项目即可接手。

标题包含多个独立目标、横跨多个决策中心、存在可并行子结果、验证方式完全不同或上下文难以一次掌握时，必须继续拆分。

### 8.2 编号

使用 `WU-<AREA>-<NNN>`。领域代号在 PLAN 中维护，编号是稳定身份，不随执行顺序调整。

### 8.3 WU 文件

复杂 WU 位于 `docs/planning/work-units/WU-AREA-NNN.md`，包含：

1. ID、领域、Phase/Milestone；
2. 背景与问题；
3. 单一目标和完成定义；
4. 输入和依赖；
5. 已确认设计与权威事实源；
6. 允许修改范围；
7. 非范围和禁止事项；
8. 兼容要求；
9. 分步任务；
10. 每步验证；
11. 整体验收；
12. 风险、失败处理和回滚；
13. 交接要求；
14. STATUS 状态链接。

WU 不保存实时状态、完成勾选、动态测试数量或重复的完整需求、Schema 和 API 定义。

## 9. PLAN、WU 与 STATUS

- PLAN 定义 Phase、Milestone、大型目标、WU 索引、依赖、风险和完成定义。
- WU 定义单个上下文单元的实施合同和验证方法。
- STATUS 保存当前 WU、状态、最新证据、阻塞、风险和下一顺序。
- 小任务仅在改变需求、公共合同、里程碑或项目实际状态时同步对应文档。

## 10. 冲突处理

已有项目中：

- 代码与测试表示当前实现；
- PRD、SPEC 和设计可能表示目标合同；
- 历史记录只说明过去过程；
- 临时文档不能自动成为正式基线。

发现冲突时记录“当前实现、目标合同、待决策差异、影响范围”，由用户决定是修正文档、保留差异还是建立新的设计/WU。Skill 不得擅自用任一方覆盖另一方。

## 11. 图表规则

仅在关系明显受益时使用图：

- 系统边界使用上下文图；
- 三个以上组件使用组件图；
- 信息域使用信息架构图；
- 复杂调用过程使用时序图；
- 领域对象使用类图或关系图；
- 多状态转换使用状态机；
- Phase/WU 依赖使用依赖图。

每张图必须附文字或表格说明参与者、职责和边界，不能成为唯一事实源。

## 12. 审计与验证

`scripts/audit_docs.py` 检查：

- 核心文档存在；
- Markdown 相对链接有效；
- docs 入口可达；
- PLAN 包含 Phase、Milestone 和 WU 索引；
- PLAN/WU 不保存完成勾选或动态状态；
- STATUS 包含结论、看板、证据、风险和下一步；
- WU ID 和必要章节符合合同；
- 没有明显的重复正式副本；
- 没有未替换占位和无效本地引用。

脚本不判断产品正确性、架构合理性、领域归属、冲突取舍或删除授权。Agent 负责人工检查事实源重复、职责混写、巨型 WU、当前与目标混写以及无意义图表。

## 13. 参考来源与项目样例

- [arc42](https://arc42.org/overview)：架构沟通模板应按项目需求裁剪，不要求机械填写全部章节。
- [C4 Model](https://c4model.com/diagrams)：根据读者和问题选择系统上下文、容器、组件、动态或部署视图。
- [Diátaxis](https://diataxis.fr/)：不同读者目标和文档目的应分离，避免操作、参考和解释混写。
- [ADR](https://adr.github.io/)：重要架构决策单独记录背景、理由、权衡和后果。
- OrchestraAgent：产品、架构、规划三层事实源；PRD/SPEC/Agent/Data/API 分工；P1–P9、领域 WU 和唯一 STATUS。
- GRS003：大型项目的主 PLAN/STATUS 入口、正式专题基线、taskbook、证据索引和领域模型。

项目样例只用于提炼方法，不把音乐生成或赛事业务内容写入 Skill。

## 14. Skill 创建与验证标准

创建时执行：

1. 使用官方 `init_skill.py` 初始化目录、references、assets 和 scripts。
2. 先运行无 Skill 的基线场景，记录过度生成文档、跳过确认、混淆事实源或创建巨型任务等失败。
3. 编写最小 SKILL.md、参考文件、模板和审计脚本。
4. 使用相同场景验证 Skill 能纠正基线问题。
5. 运行 `quick_validate.py`。
6. 测试 `audit_docs.py --help` 和临时项目样例。
7. 检查 `agents/openai.yaml` 与 SKILL.md 一致。

至少覆盖三个场景：

- 小型新项目，不应过度创建条件型文档；
- 文档重复的已有项目，应先给方案、保留来源并建立迁移矩阵；
- 跨 API、数据和前端的大型目标，应拆成多个 WU，而不是巨型任务。

## 15. 完成标准

- 用户已确认组织或迁移方案；
- 文档套餐选择有明确依据；
- 每类事实只有一个详细权威来源；
- 新项目没有空洞模板；
- 已有项目迁移矩阵能追踪全部有效内容；
- 旧文档只在验证后归档或删除；
- 大型目标已拆成上下文可控的 WU；
- PLAN、WU、STATUS 职责清晰；
- 当前实现与目标合同差异已显式记录；
- 文档入口和相对链接有效；
- 自动审计通过，或明确说明无法自动验证部分；
- 未覆盖用户工作，未执行未经授权的 Git、删除或部署操作；
- 最终交付列出修改文件、验证结果和剩余风险。

## 16. 设计边界

- Skill 不替代具体项目的产品、架构或领域判断。
- Skill 不强制所有项目使用完全相同的文件名和目录。
- Skill 不把文档数量当作项目成熟度指标。
- Skill 不把审计脚本的通过等同于内容正确。
- Skill 不自动执行真实部署、远程提交或大范围删除。
